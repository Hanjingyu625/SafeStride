# 2026-09-28 양손 접촉 중 armed=false 원인 분석

오늘 실행 중인 Pi와 `power_test_20260928_174222`의 18:06–18:14(KST) 구간을 읽기 전용으로 분석했다. 녹화·구동 서비스·파라미터는 변경하지 않았다. Pi 저장소 HEAD는 `cb779b7`이며 어제 분석한 로컬 코드와 다르다. 실제 실행 바이너리 해시는 확인하지 않았다.

## 결론

ToF 정지는 실제 ROS 파라미터에서 `terrain_stop_enabled=false`다. 그러나 이것은 압력 외의 주행 허가 조건을 해제하지 않는다. **오늘은 저전압 경고와 직렬 통신 장애가 실제로 발생했고, 통신이 정상인 구간에도 MCU 정지 조건 때문에 ARM이 거부되는 사례가 있다.** 어제의 ARM 정지 조건만으로 오늘의 모든 현상을 설명해서는 안 된다.

## 확인한 증거

### 1. 저전압·직렬 통신 장애·재연결

Pi 커널은 18:08:30, 18:09:07, 18:09:21, 18:09:29, 18:10:04, 18:10:57, 18:11:12, 18:12:36, 18:12:54에 `Undervoltage detected!`를 기록했다. 이후 각각 정상화 로그도 있다. 이는 Pi의 전원 이상이 실제 감지됐다는 근거다. MCU 메시지의 `fault_bits=0`과 모순되지 않는다. 둘은 다른 장치의 진단이다.

| Drive 상태 수신 공백(KST) | 길이 | 서비스 로그 |
|---|---:|---|
| 18:08:32.303–18:09:02.817 | 30.514초 | 18:09:02 `serial link closed: Write timeout` |
| 18:09:31.510–18:10:02.207 | 30.696초 | 18:10:02 같은 오류 |
| 18:10:24.358–18:10:54.934 | 30.577초 | 18:10:54 같은 오류 |
| 18:13:02.395–18:13:32.635 | 30.240초 | 18:13:32 같은 오류 |

이때 감독 노드는 `status_stale`을 내고 목표 0·명령 발행 억제로 전환한다. 예를 들어 18:08:53의 진단은 과거 `deadman=true`를 여전히 담고 있지만 `status_age_s=21.006`이다. **화면에서 접촉 true가 보여도 21초 전 정보일 수 있다.** 실시간 양손 접촉으로 간주하면 안 된다.

복구 중 boot_id=0은 브리지가 상태를 초기화한 값이며 재부팅 횟수로 세면 안 된다. 0을 제외한 실제 boot_id는 이 구간에서 네 번 새 값으로 바뀐다. MCU 재시작과 맞는 증거지만 전압 강하의 직접 리셋인지, 직렬 포트를 다시 열며 발생한 DTR 리셋인지는 구분되지 않는다. 코드에도 포트 재개방 시 Uno 리셋 가능성을 설명하는 주석이 있다.

서비스 로그에는 18:09:09, 18:09:10, 18:09:21, 18:10:05, 18:10:11, 18:10:17, 18:10:59, 18:11:12, 18:12:37, 18:12:55에 `mcu_watchdog_timeout`도 있다. 2Hz 진단 로스백만 보면 일부 짧은 이벤트가 빠진다.

해석: 저전압과 통신 장애의 시간적 연관성이 강하다. 다만 USB 케이블·허브·배선·드라이버·전원 분배 중 정확한 고장 지점이나 30초 I/O 정체의 내부 원인은 아직 확정되지 않았다. 소스의 `write_timeout=0.20`만 보고 실제 장애 처리가 200ms 안에 완료된다고 가정하면 안 된다.

### 2. 실제 양손 접촉인데도 정지 조건 때문에 ARM 대기

18:09:12.831의 기록:

| 항목 | 값 |
|---|---|
| 왼쪽/오른쪽 압력 raw | 672 / 689 |
| 왼쪽/오른쪽 접촉 | true / true |
| deadman / armed | true / false |
| Hall 측정속도 | 0.204m/s |
| 마지막 펄스 나이 | 1.47초 |
| Drive 명령 | DRIVE, 목표 약 0.416m/s, PWM cap 80 |
| 적용 PWM | 0 |
| fault / watchdog | 0 / false |

다음 감독 진단에서도 `disarmed, uphill_assist_limited`, 신선한 status, 양수 목표가 확인된다. 즉 압력 부족이나 ToF 정지로 설명할 구간이 아니다.

Pi에 있는 MCU 소스는 일반 DRIVE의 ARM 시 정지 대기를 요구한다. 기준은 약 0.0115m/s 이하를 250ms 유지하는 것이며, Hall은 마지막 속도를 최대 5초 유지한다. 위의 0.204m/s는 정지 조건보다 높다. 천천히 밀거나 멈춘 직후라면 손을 잡아도 ARM이 거부될 수 있다. 18:07:20.185–18:07:26.796에도 양손 접촉·비무장이 6.611초 이어지고 Hall은 0.055–0.077m/s였다.

18:08:20.181–18:08:23.771에는 양손 접촉·비무장 대기 후 마지막 펄스 나이가 약 5.25초에 이르러 ARM으로 복귀한다. 기존 Hall 5초 유지와 정지 dwell 해석에 부합한다.

세션 ID는 분석 구간에서 45회 바뀌었다. 오늘은 통신 장애와 MCU 재시작도 있으므로 45회 전체를 ARM 거부 때문이라고 분류하지 않았다.

### 3. ToF 비활성과 IMU 경사 제어는 별개

실제 ROS 파라미터는 `terrain_stop_enabled=false`, `slope_control_enabled=true`다. 따라서 ToF를 사용하지 않아도 경사 제어는 계속 동작한다. 현재 설정은 내리막 7° 진입 시 3초 PWM 감속, 3° 이하 0.5초 유지 후 복귀다.

18:08:01.693에는 `armed=true`, `deadman=true`인데 `downhill_pwm_off, slope_ramp_stop`으로 목표가 0이다. 이는 ARM 해제와 구분해야 한다. 경사 정지 자체를 이번 모든 `armed=false`의 직접 원인으로 지목할 근거는 없다. 오르막 진단의 `uphill_assist_limited`도 그 자체가 ARM 거부 원인은 아니다.

### 4. 출발 보조 시계 문제는 남아 있음

현재 Pi 감독 소스도 양손 접촉 시 4초 출발 시계를 시작한다. 따라서 ARM 대기·지형 정지 중 출발 시간이 소진되어, 나중에 ARMED가 돼도 PWM cap 0으로 남을 수 있다. 이 문제는 'ARM이 false'와 'ARM은 true인데 안 움직임'을 구분해서 다뤄야 한다. 어제 기록에서 확인한 구체 사례는 `20260927/ROSBAG_REVIEW_KO.md`에 있다.

## 조치 권고

1. **전원과 Drive 직렬 경로를 먼저 점검한다.** 모터 부하가 변할 때 Pi 입력 전압 강하를 측정하고, 전원 공급 여유·전원 케이블·커넥터·USB 연결을 확인한다. 안정된 전원 조건에서 동일 시험을 비교해 저전압·write timeout·상태 공백이 사라지는지 확인한다. 현 상태에서 PWM이나 ARM 허용속도를 먼저 높일 근거는 없다.
2. **장시간 I/O 정체를 상태 발행과 분리한다.** serial 쓰기 실패가 상태 갱신까지 묶어 두는지 검사하고, 링크 상태·마지막 수신 나이를 독립적으로 발행한다. watchdog·status timeout을 늘려 증상을 숨기지 않는다.
3. **ARM 허가와 통신 세션 생존을 분리한다.** 정지 대기 중에도 검증된 세션 유지는 가능하도록 하되 추진 허가·구동 watchdog 조건을 완화하지 않는다. `arm_inhibit_reason`과 정지 대기 진행 상태를 노출한다.
4. **속도 유효성과 출발 시간을 정리한다.** 오래된 속도, 정지 추정, 실제 구동 가능한 출발 구간을 구분한다. 출발 보조 제한을 단순히 손 접촉 시각부터 계산하지 않도록 설계하되 무제한 통전은 막는다.
5. **표시를 분리한다.** 양손 접촉, 상태 수신 유효성, ARMED, 실제 PWM, 경사 감속을 각각 보여준다. 상태가 오래되면 마지막 true/false를 정상 실시간 값처럼 표시하지 않는다.

현재 임시 확인은 평지에서 바퀴를 움직이지 않은 채 안정된 전원·신선한 상태를 확보한 후 양손을 잡고 비교하는 것이 유용하다. 이것은 진단용 재현 방법이며, 5초 기다리거나 계속 재접촉하는 것을 근본 해결책으로 삼아서는 안 된다.

## 집계 주의

18:06–18:14에는 0.5초를 넘는 상태 공백이 합계 약 125.17초 있다. 이 시간을 과거 deadman/armed 값으로 채워 넣으면 '양손인데 비무장' 시간이 과장된다. 해당 공백을 제외한 관측 간격에서 양손 접촉·비무장은 약 56.32초였다. 공백 동안 실제 손 접촉이나 MCU 상태는 직접 관측되지 않았다.

분석 근거는 오늘 MCAP 메시지, `journalctl -u safestride.service`, 커널 저전압 로그, 실제 ROS 파라미터, Pi 소스다. 코드·설정 변경이나 서비스 재시작은 수행하지 않았다.
