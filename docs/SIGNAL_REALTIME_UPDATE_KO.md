# 실시간 신호 API 및 판단 변경 (2026-09-29)

## 실제 확인 결과

사용자가 승인받은 두 실시간 API를 기존 저장 키로 직접 확인했다.
승인 화면의 키 문자열과 로컬 `raspberry_pi/api_key.txt`가 일치했다.
광진구청 교차로 1697 조회에서 두 API 모두 HTTP 200을 반환했다.
이어 수정한 클라이언트로 약 1초 간격 5회 조회하여 모두 정상 수신했다.
동/서 보행신호는 빨간불이었고 잔여시간은 36001(사용 불가)이었다.
빨간불은 잔여시간 없이도 확인되므로 이 응답은 '신호 없음'이 아니라 '기다려'다.
녹색 판정은 테스트 데이터로 검증했으며, 이번 실제 5회 수신은 모두 빨간불이었다.

## API와 자동 실행

기본 요청 주소는 승인 화면과 동일하다.

- 현시: `https://t-data.seoul.go.kr/apig/apiman-gateway/tapi/v2xSignalPhaseCurrentInfo/1.0`
- 잔여시간: `https://t-data.seoul.go.kr/apig/apiman-gateway/tapi/v2xSignalPhaseTimingCurrentInfo/1.0`

둘 다 소문자 `apikey`와 동일한 `itstId`로 병렬 조회한다.
2026-09-29 호출량 제한 실측 후 `signal_refresh_interval_s`를 3초로 조정했다.
횡단보도 좌표 37,311개는 로컬 JSON을 사용하고 교차로 지도는 디스크 캐시를 재사용한다.
선택 횡단보도 가장자리 20m 밖에서는 신호 API를 호출하지 않는다.
20m 안의 첫 조회와 빨간불 상태에서는 현시 API만 호출한다. 현시가 녹색일 때만
현시와 잔여시간 API를 함께 호출한다. 서버 응답 사이의 잔여 초는 원본 UTC 시각과
로컬 시각 차이를 빼서 계속 갱신하므로 화면 주기마다 API를 부르지 않는다.
타이머/작업 스레드 시작 차이는 다음 타이머에서 재확인해 불필요한 오류로 표시하지 않는다.
요청이 늦으면 이전 요청 종료를 기다리므로 항상 정확히 1Hz를 보장하는 것은 아니다.

원본 시각은 관측 중 약 2초 단위로 갱신되기도 했다. 1초 조회가 서버 갱신을
빠르게 만들지는 않는다. 동일 응답을 새 데이터로 취급하지 않고 원본 시각을 사용한다.
HTTP 429는 응답 JSON 내부 `X-RateLimit-Reset`도 읽는다. 2026-09-29 15:59:40 KST의
실제 응답 `28819초`는 23:59:59 KST에 해당하여 현재 제한은 자정 초기화로 관측됐다.
로컬 캐시 삭제로 서버 사용량은 초기화되지 않는다.
신호를 잃어도 오래된 데이터를 계속 유효하게 연장하지 않는다.

## 횡단보도와 신호 그룹 매칭

서울시 공식 설명에서 보행신호 방향은 횡단보도 자체의 방위가 아니다.
차량이 직진할 때 그 횡단보도를 오른쪽에 두는 진입 방향의 신호 그룹을 사용한다.
따라서 교차로 서쪽 횡단보도는 `wtPdsg*`가 아니라 `ntPdsg*`에 해당한다.
코드는 교차로 중심에서 횡단보도로 향하는 방위에 90도를 더한 뒤,
횡단보도 장축과 일치하는지 확인해 `nt/et/st/wt` 또는 대각선 그룹을 고른다.
기하가 애매하면 한 방향을 임의로 고르지 않고 가능한 양쪽 현시가 일치할 때만 유효하다.

공개된 `신호연결 MAP 정보` CSV도 확인했으나 차량 차로의 직진/좌회전/우회전 연결만
포함하고 보행 횡단보도 좌표나 보행신호 연결은 포함하지 않는다. 이 파일은 현재
보행신호 매칭을 대체할 수 없다.

신호 주기는 시간대, 보행자 버튼, 교통 대응 및 현장 설정에 따라 달라질 수 있으므로
관측한 반복 주기를 실제 녹색 또는 진입 허가로 사용하지 않는다. 대회 시연도 20m 안에서
받은 실시간 현시를 사용하며, API가 없으면 `신호 없음`으로 표시한다.

기존 `scripts/run.sh`와 서비스 시작 방식은 그대로 사용한다. 키는 매번 입력하지 않는다.
노드 자체도 다음 순서로 저장된 키를 자동 로드한다.

1. 명시한 `api_key_file`, 또는 `SAFESTRIDE_SIGNAL_API_KEY_FILE` 경로
2. 별도 지정이 없으면 `/etc/safestride/signal_api_key.txt`
3. 위 기본 파일에 키가 없으면 체크아웃의 `raspberry_pi/api_key.txt`

명시한 경로가 잘못됐을 때 다른 키로 몰래 바꾸지는 않는다.
run.sh가 전달하는 키 경로가 있으면 그 경로가 우선한다. 서비스 재시작 시 자동으로 읽는다.
현재 저장 키가 새 승인 키와 같으므로 키 내용 교체는 필요하지 않았다.

## 직관적인 판단

| 상황 | guidance decision | 표시 |
|---|---|---|
| 진입 지점에서 녹색이고 필요한 시간이 충분 | GO | 건널 수 있음 |
| 진입 전 빨간불 또는 녹색 시간이 부족 | WAIT | 기다려 |
| 횡단 중 남은 시간이 부족하거나 ETA/완료 확인 불가 | CAUTION | 주의 |
| 신호 누락, 오래된 신호, 방향/현시/필수 잔여시간 미확정 | NO_SIGNAL | 신호 없음 |

접근 중에는 진입 지점에서 재확인하도록 WAIT를 유지한다.
선택된 횡단보도가 없거나 횡단 완료 상태에는 NONE/안내 없음이다.
횡단 중 신호가 사라지면 NO_SIGNAL로 실제 신호 확인을 안내한다.
이미 도로 위에 있을 때 진입 전 '기다려' 판단으로 되돌리지 않는다.

진입 필요시간 = 횡단보도 길이 / 사용자 보행속도 + 반응 1초 + 여유 2초.
사용자 속도는 확인된 이동 표본의 중앙값이며, 대기 속도는 학습하지 않는다.
표본이 없을 때 기존 기본값 1.0m/s를 사용한다. 이 값은 실제 모터 속도 보장이 아니다.
예: 길이 10m, 사용자 속도 1m/s이면 13초가 필요하다. 남은 녹색 18초면 진입 가능,
10초면 대기다. 속도가 0.35m/s이면 약 31.6초가 필요하므로 18초에는 대기한다.

횡단 중 ETA = 남은 거리 / 현재 측정속도.
남은 녹색이 ETA + 2초보다 짧으면 주의다. 정지/속도 누락은 ETA 미확정이다.
시간 계산과 여유값 자체는 이번 변경으로 늘리거나 줄이지 않았다.
녹색은 실제 현시 이름으로 확인하고, 유효한 잔여시간에서 원본 데이터 나이를 뺀다.
36000/36001/-1은 잔여시간으로 사용하지 않는다. 빨간불의 남은 시간을 녹색 시간으로 쓰지 않는다.

## 호환성과 확인

`/crosswalk/status`의 내부 state 0~6, 횡단 시작/완료, GPS 후보 유지,
바퀴 이동 확인, 모터 제어 및 LCD 통신 형식은 유지한다.
LCD는 기존 status의 signal_valid/state를 계속 받는다. LCD 문구 자체는 변경하지 않았다.
사람이 읽을 판단은 `/crosswalk/guidance`의 decision/state/reason으로 확인한다.
signal_color는 RED/GREEN/UNKNOWN, 나머지 계산값과 매칭 원인도 함께 제공한다.
지도 기반 신호 방향은 공식 규칙에 맞춰 계산하지만 입력 좌표 오차가 있으므로
대회 전 대상 횡단보도에서 실제 신호등과 한 번 대조해야 한다.

```bash
ros2 topic echo /crosswalk/guidance
```

서비스와 중복 조회하지 않는 별도 점검 시 저장 키를 자동으로 사용한다.

```bash
python3 tools/probe_signal_current.py --intersection 1697 --samples 5
```

이 도구는 운영 코드와 같은 조회/파싱/오류 대기 로직을 사용하고 최대 30회로 제한한다.
구형 API를 조회하던 legacy-check 및 키 인자 대소문자 수동 선택 옵션은 제거했다.

검증: GPS/내비게이션 자동 테스트 통과. 실제 API 5회 연속 수신 성공.
이 변경의 Pi 재배포/현장 주행 결과를 의미하지는 않는다.
